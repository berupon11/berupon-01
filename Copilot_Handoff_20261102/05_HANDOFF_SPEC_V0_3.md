## 0. この文書の使い方・優先順位

この文書は、2026-10-31作成の `00_README.md`～`04_COPILOT_START_PROMPT.md` と、その後の検討で定まった内容をつないだ引継ぎ資料である。**矛盾があれば、この文書に記載した最新の運用決定を優先**する。ただし、資料にない詳細をCopilotが推測して決定してはならない。

- **決定**：本プロジェクトで採用する構想・初期運用上の方針。設備メーカー・MESベンダーと合意済みの要求とは限らない。
- **試作の現状**：実ファイルから確認できる実装内容。決定された方針をすべて満たすとは限らない。
- **暫定シナリオ**：要求定義の議論を始めるための動作例。装置共通の実装要求ではない。
- **未決**：関係者との確認・判断が必要な項目。勝手に補完しない。
- **提案**：引継ぎ後に検討する実装・運用案。確定事項と区別する。

## 1. プロジェクトの目的と対象

### 1.1 目的

製造装置・MES・将来の搬送システムについて、動作、状態、情報授受をシミュレーター上で確認する。工程担当者は、自分の装置と標準シナリオの違いや疑問を**その場で該当Stepに記録**する。記録を基に主導者がモデルを改訂し、要求候補を整理して装置メーカー・MESベンダーとの協議につなげる。

シミュレーターは**関係者の認識を合わせるための道具**であり、現段階で製造装置の制御仕様を確定するものではない。

### 1.2 初期対象外

SECS-IIの具体的コマンド、GEM/GEM300のメッセージ実装詳細、PLC内部ロジック、精密なタクト計算、MESのDB・画面内部設計、AGV・ストッカー内部の詳細動作、企業システムへの自動連携は対象外。後続で必要になれば別途検討する。

### 1.3 権限と判断主体

- **プロジェクト主導者（ユーザー）**：標準モデルのStep追加・変更・削除、装置マスターの準備・管理、共通動作IDの割当、コメントを反映するかの判断、Copilotによる改訂案の確認。
- **工程担当者**：標準シナリオを閲覧し、対象装置を指定してStep別の相違点・疑問・不足動作を記録する。標準Stepは編集しない。
- **会社Copilot**：実装・データ改訂の下書き、指示された機能の追加・検証補助。独自に要求を決定・承認しない。
- **正式な承認権限者**：別途明確化が必要。主導者がすべての正式要求を承認できるとは仮定しない。

## 2. 確定したモデル設計方針

### 2.1 3階層モデル

| 階層 | 意味 | 現段階の扱い |
| --- | --- | --- |
| L1 共通モデル | 現物、装置、MESの状態・動作・情報授受などの共通概念 | 基礎方針を整理。汎用スキーマは発展途上 |
| L2 装置類型別モデル | 単枚処理・バッチ・インライン複合等の代表骨格 | **単枚処理装置のL2代表モデルを試作** |
| L3 工程・個別装置モデル | 個別の制約や動作差分 | 工程担当者のレビューから段階的に具体化。現段階では未完成 |

分類名や装置類型の網羅範囲は今後更新し得る。L2を全装置の必須動作として扱わない。

### 2.2 階層型Step

- 親Stepは**表示・整理用のグループ**であり、それ自体は実行しない。
- 末端Step（leaf）だけが、現物・装置・MESの状態変化、情報授受、分岐を表す。
- Step IDは表示順から独立した固定識別子とし、順番を変えてもコメント参照先を変えない。
- `equipmentDefinition`（構成）と `initialState`（初期状態）を分け、各leafの `changes` を適用して現在状態を再現する。**現行のフィールド名は試作上の暫定実装**。
- 同じシナリオデータから複数の画面表示を生成することを原則とする。簡易シーケンスビューは当初要求にあるが、現行試作の完了機能として扱わない。

### 2.3 3種類の状態を区別

1. **現物（`physical`）**：カセット・基板の実際の位置や状態、LP開閉、装置内残留など。
2. **装置の認識（`equipment`）**：装置がセンサーや照合で把握している情報・制御上の状態。
3. **MESの認識（`mes`）**：MESが通知を受けて把握したロット・カセット・基板・設備の状態。

現物・装置・MESの情報更新タイミングは一致するとは限らない。通知したStepとMES側が認識を更新したStepを区別する。

### 2.4 表示方式

- スマートフォンで確認済みの縦方向レイアウトを基準にする。上から「現在のStep／操作」「MESの認識」「装置・現物の概念図」とし、情報授受・Stepツリー・コメントを閲覧できる。
- LP1、LP2、EFEM、処理部、外部AGVを視覚化する。**先行処理中のLP1という架空の初期状態は削除済み**。
- 初期状態ではLP1、LP2とも空き。代表シナリオで使用するのはLP2のみ。別カセットの同時搬入・処理は表現しない。**同時搬入を装置仕様として一律禁止する決定ではない**。
- PCでのレイアウト最適化は後続。スマートフォンで見やすいこととPCでの操作性を混同しない。

## 3. L2代表シナリオの内容（確定方針と暫定案を分ける）

### 3.1 モデルの前提

- 仮の代表装置 `EQ-001`：LP1/LP2、EFEM 1基、処理部1基。AGVは装置外部。
- カセットは12スロット。上段を12、下段を1とし、空きスロットを飛ばして上から処理する。
- 試作データでは8枚の基板を逐次処理し、処理後は元スロットへ返却する。**逐次処理は再生モデルの簡略化であり、実装装置の並列処理禁止を意味しない**。
- 基板ID読取可能な装置を例にする。読取不能装置の例外経路は未作成。

### 3.2 グループ別の動作

| 親Step | 主な動作 | 留意点 |
| --- | --- | --- |
| 01 カセット受入 | MESから予定カセットID送付 → AGVがLP2へ設置 → 物理受渡し成立 → AGV離脱 → 装置でカセットID読取・照合 → 結果通知 → MESが受入完了を認識 | **AGV離脱は物理受渡し完了に依存し、ID一致には依存しない**。ID読取とAGV離脱の詳細順序は未決。試作順序は例示にすぎない |
| 02 処理準備 | MESが期待スロット構成・処理予定・レシピ等を事前送付 → LP開蓋 → 直後のスロットマッピング → 装置で照合・MESへ結果通知 → 装置内でCJ/PJ作成・通知 | 装置が照合OKならMESの通知受領確認を待たずに進む想定。CJ/PJのMES事前承認を省くかは未決の暫定案 |
| 03〜05 基板搬送・処理・回収 | 上側の実在スロットから取出し → 処理前の基板ID読取・照合 → 処理開始通知 → 処理 → 処理完了通知 → 元スロットへ返却 → 次の基板へ | ID不一致時は処理開始しない。処理部到着・処理開始・処理完了・元スロット返却は別の出来事 |
| 06 最終照合・閉蓋・搬出 | 全基板処理／回収を確認 → **閉蓋前に最終スロットマッピング** → 照合結果記録 → 装置内の残留基板等の安全確認 → 条件成立なら閉蓋 → 結果通知 → 搬出 | **スロット照合NGでも、閉蓋安全条件を満たせば閉蓋する**。照合NGと閉蓋不可は別の判定 |

### 3.3 最終照合での異常分岐：合意した初期方針

| 最終スロット照合 | 閉蓋安全条件 | 装置動作・扱い |
| --- | --- | --- |
| OK | 成立 | 閉蓋し、正常経路で搬出。正常時の搬送先は未決 |
| NG | 成立 | 異常を記録し、閉蓋・搬出する。搬送先は**原則ストッカー**。ストッカーでの対応内容は未決 |
| OK | 不成立 | 閉蓋せず停止する方針をモデル化。詳細条件は未決 |
| NG | 不成立 | 不一致を記録し、閉蓋せず停止。閉蓋できない原因・復旧手順は未決 |

閉蓋安全条件の検討例：EFEM搬送機構上、アライナー上（装備する場合）、処理部内などに、閉蓋に支障となる基板が残っていないことを検知できる。具体的なセンサー・判定ロジックは装置類型／個別装置の設計に依存する。

**閉蓋・搬出の許可は、処理結果の正常判定や次工程への進行許可と同義ではない。** 次工程のホールド要否・解除主体等は別途判断が必要。

### 3.4 処理開始を巡る重要な未決

MESからの事前情報を用いて装置がCJ/PJを生成し、そのまま自律的に処理へ進む流れは、討議のための暫定モデルである。MESによる作成内容・レシピ・ホールド等の確認と、処理開始前の許可ゲートの要否は未決。**後追いの結果通知だけで誤レシピ実行を防げるとみなさないこと。**

## 4. コメント登録・レビュー運用：最新の決定

### 4.1 初期運用の基本ルール

1. 標準Stepは工程担当者に対して**閲覧専用**。Stepの追加・修正・削除は主導者が行う。
2. 工程担当者は、画面で表示しているStepに対して「相違点／確認事項／不足する動作」をコメントとして記録できる。
3. **1コメントにつき1装置**を必須選択する。**1コメントファイルにつき1装置**とする。
4. **記録者が誰かを明確に残す**。対象装置・記録者はファイル内の記録項目とファイル名から識別できるようにする。
5. コメントは全工程担当者が閲覧可能な共有場所に保存する。ただし、初期段階で**自動同期や複数ファイルの自動集約は行わない**。共有フォルダ上のファイルを閲覧する運用で開始する。
6. ファイルの保管先は、会社MES専用Teamsに紐づく**所定のSharePointフォルダ**。詳細パス・権限は会社側で指定・確認する。個人のOneDriveは作業領域に限り、正本を置く先と混同しない。
7. コメント登録は**標準シナリオそのものの改訂・仕様承認を意味しない**。

### 4.2 複数装置に共通する指摘の例外運用

同じ指摘を複数の装置に個別入力する負荷が高い場合、工程担当者は**Teamsまたはメールで自然言語の文章として**主導者に連絡してよい。少なくとも対象装置、異なる箇所／Stepや動作、どう違うか、どの装置に共通するという主張か、反映してほしい内容が読み取れるようにする。定型入力や自動取り込みは求めない。

**口頭だけの指示は受け付けない。** 文書で残された「共通化してほしい」という要望は、共通化の決定ではない。採否と標準Stepへの反映は主導者が判断する。

### 4.3 装置マスター

- 主導者が会社側で正式な装置マスターを準備する。
- 装置類型をマスターでグループ化する。現在のL2シナリオに対応する類型の装置のみ選択候補に出す。
- 1類型の選択肢を**おおむね10種類程度**に抑えられる分類を目指す。厳格な最大10件制限は決定していない。
- 装置ID・装置名称・類型IDは必要な管理項目。利用可否／選択対象外の区別も試作で利用中。
- **装置名だけでなく安定した装置IDをコメントに保存**する。仮の装置名・IDを正式情報として利用しない。

### 4.4 コメントの識別・検索

- コメントは `commentId`、`scenarioId`、`stepId`、`equipmentId`、区分、本文、記録者、記録日時等を関連付ける構成を基本とする。
- まず「現在のStepのコメント」と「全Stepからのキーワード検索」「装置による絞り込み」を扱う。
- **共通動作ID（`commonActionId`）は任意**。主導者が比較してよいと判断できたStepにのみ明示的に付ける。
- 未設定は「未分類・未判断」であり、「共通性がない」という意味ではない。同じIDが付いても装置の仕様が同じと保証するものではない。
- 共通動作IDを使った横断比較は**明示的に分類されたStepだけ**を対象にし、その限定を検索結果に表示する。
- 将来の自動類似判定や無理な一括分類は初期対象外。**検索の便利さより誤解の少なさを優先**する。

### 4.5 ファイル形式・命名（初期実装の方向性）

- 初期の機械読込・再編集用ファイルは**JSONを主形式とする案を継続**。Markdownはレビュー用の可読な出力として扱えるが、編集・再読込の正本形式と混同しない。既存v0.1の「コメントMarkdown」案をそのまま実装必須としない。
- **装置別に1ファイル**とし、ファイル内にも `equipmentId`、装置名、記録者、作成日時を記録する。コメントの各行にもStep ID等を保持する。
- ファイル名の例（案）：`<装置ID>_<記録者名>_<作成日時>.json`。禁則文字の除去、同名重複、再提出時の版管理は実装前に安全なルールを設計・確認する。
- 同じ装置に関する複数のコメントは1ファイル内に含めてよい。ただし**別の装置に属するコメントを同じ出力ファイルへ混ぜない**。
- 出力と再読込の試験では、異なる装置のコメント混入、誤ったStep IDの紐づけ、文字化け、上書き・消失がないことを確認する。

## 6. 既知の実装不足・リスク（Copilot側の作業対象）

### P0 — 最初に直す（個別記録運用の成立条件）

| ID | 不足・問題 | 期待する状態 |
| --- | --- | --- |
| IMP-01 | JSON出力が`review_comments.json`に**全装置のコメントを一括出力**する | 選択した装置のコメントだけを1ファイルに出力。混在・誤選択を防ぐ |
| IMP-02 | 記録者名の入力が任意 | コメント登録または提出時に記録者が未設定なら提出できない。詳細な入力タイミングは実装案を提示する |
| IMP-03 | ファイル名とファイル内部で装置・記録者・作成日時を特定できない | 安全な自動命名と、明示的な出力メタデータを備える。出力データのスキーマは改訂案を提出する |
| IMP-04 | `equipment_master.json` はHTML内埋込の複製であり、**外部ファイルだけを編集しても画面に反映されない** | 会社PCのローカルブラウザ制限を踏まえ、マスター差替手順を一つに定める。読込UI方式・生成方式等は検証後に決定 |
| IMP-05 | ブラウザ内コメントが自動保存されず、未出力データの消失リスクがある | 出力漏れを防ぐ案内・確認動作を設ける。自動同期は要らない |
| IMP-06 | 複数の装置コメントを扱える現行UIが、1ファイル1装置の運用を保証しない | 装置ごとの作業／出力境界を明確にし、混在・取り違え防止をテストする |

### P1 — 会社環境での検証と最低限の品質確認

| ID | 確認事項 | 注意 |

| VER-02 | コメントJSONを再読込して、装置・Step・記録者・文字列が保たれるか | 同一コメントID、スキーマ互換、改訂後のStep IDを確認 |

### P2 — 今回は保留（将来の候補）

複数の装置別コメントファイルの自動集約・自動同期、Teams/メールからの自動取込、複数装置への一括コメント登録、類似コメントの自動判定、要求候補の正式な状態管理、議事録・判断主体・要求文の完全な追跡、版間差分表示、詳細なシーケンスビュー、PC専用の高度な画面配置、装置の他類型／搬送設備の拡張。**これらを初期運用の開始条件として勝手に追加しない。**

### 現行実装で取り扱い注意

- `index.html` が`scenario.json`と`equipment_master.json`の内容を内部に持つ。同梱JSONの更新はHTML画面への自動反映を意味しない。
- コメントのインポートはコメントID重複の際に追加しない処理で、変更差分の統合や共同編集の競合解決ではない。
- コメント出力ファイルは現在、装置に関係なく全件。**新運用の提出物としてそのまま使わない**。
- `commonActionId` は試作データで全Step未設定。横断検索を動かすためだけに自動付番しない。
- シナリオとコメントの現在のスキーマは試作版。変更時は既存データの扱いを明示する。

## 8. Copilotに最初に依頼する作業（順序指定）

**作業を始める前に**、必ず `00_README.md`～`04_COPILOT_START_PROMPT.md`、本書、既存試作ZIPを確認し、v0.1とv0.3の差異を提示する。仕様に疑問があれば、独断で要件を追加せず「質問／実装上の提案」として分ける。

1. **現状把握**：v0.2のHTML内埋込データ、JSON形式、Step・コメントの関連を確認し、破壊的変更を避ける。異なる表記・数値は実ファイル優先で報告する。
2. **装置別コメント出力**：装置を1つ選んで、その装置に属するコメントだけを出力できるようにする。記録者・日時等の識別メタデータを追加し、誤出力を防止する。
3. **記録者必須化**：未入力時の動作を実装し、出力時に未記名データが残らないようにする。既存データの移行方法も提示する。
4. **マスター差替方法**：外部JSON編集と画面が連動しない現状を解消する案を提示し、会社PCで実際に使える方式を検証する。マスター管理権限は主導者に限定する運用を守る。
5. **基本試験**：正常・最終照合NG安全／危険分岐、Step送り戻し、コメント作成、装置別出力、再読込を確認する。
6. **会社環境検証**：SharePoint格納／再参照、Copilotでの改訂JSON作成、シミュレーターでの再読込を検証する。不可なら理由と代替手順を報告する。
7. **引継ぎ結果**：変更ファイル、実装済／未実装、試験結果、未決事項、次の判断依頼をまとめて主導者に提示する。

**禁止する先回り実装**：自動集約、複数装置への一括登録、共通動作IDの自動分類、正式要求の自動承認、SharePoint自動同期、会社固有の実装を外部GitHubへ公開すること。
